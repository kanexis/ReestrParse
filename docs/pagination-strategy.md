# Стратегия пагинации

## Проблема старой реализации

Старый crawler искал нужную организацию на странице, открывал её в том же tab, затем делал `Back()`. ЕИАС восстанавливал каталог с первой страницы, поэтому для организаций со страниц 2/3/... пагинация проходилась повторно.

## Текущая стратегия

### Catalog phase

1. Применить регион/сферу/форму.
2. Отдельно нажать `#searchBtn`.
3. На каждой странице прочитать текущий `ASPxGridView2`.
4. Одновременно попытаться получить DevExpress row key и сформировать прямой `DetailUrl`.
5. Перейти строго на следующую страницу через штатный DevExpress callback `PBN` (`Следующая`); при необходимости fallback — видимая кнопка `Следующая`, затем client `NextPage`.
6. Не открывать карточки организаций во время catalog phase.

Пагинация выполняется ровно один раз.

### Details phase

После завершения каталога browser position больше не имеет значения. `OrganizationReference[]` передаётся worker pool, а каждый worker открывает карточку напрямую по `DetailUrl`.

Таким образом сложность details phase больше не зависит от номера страницы, на которой организация находилась в каталоге.

## Почему catalog не параллельный

DevExpress pager — состояние одной web session. Параллельный доступ нескольких потоков к одному `IWebDriver` создаёт callback/stale races.

Параллельность переносится туда, где задачи независимы: обработка уже найденных карточек организаций.


## Details worker navigation (v0.9.4)

Для fallback-поиска организации `SourcePage` остаётся hint. Переход Worker на целевую страницу выполняется в три уровня:

1. `ASPxGridView2.GotoPage(target - 1)` через клиентский DevExpress API.
2. Если дальний callback не подтверждён — последовательные `NextPage` / `PrevPage` (с `GotoPage` как client fallback) до целевой страницы.
3. Selenium-клик по `a.dxp-num` применяется только если нужная numeric-link реально видима в текущем pager.

При трёх pager failures за десять секунд общий `EiasCatalogBackoffGate` на 12 секунд притормаживает новые catalog-попытки всех details workers. Это предотвращает лавину повторных фильтраций/переходов при деградации DevExpress callback-ов.

## v0.9.5: переход через ближайшую видимую страницу

DevExpress pager не обязан отрисовывать ссылку на далёкую страницу. Поэтому details-worker сначала читает реально видимые `a.dxp-num`/`b.dxp-num`, выбирает ближайшую видимую страницу в направлении цели и кликает её. После callback pager полностью перечитывается.

Пример: если на page 1 требуется page 8, но видимы только 1..7, выполняется `1 -> 7 -> 8`, а не попытка найти отсутствующий `<a>8</a>` и не обязательный проход `1 -> 2 -> ... -> 8`.
## v0.9.6: разделение catalog и worker navigation

Основной catalog crawler всегда идёт по порядку, поэтому для него не используется алгоритм дальних переходов. На каждом шаге вызывается только переход на следующую страницу и затем проверяется фактический `Страница N of M`. Это предотвращает регресс, когда сложная worker-навигация мешала обычному переходу `3 -> 4`.

`visible pager hops` остаются только в details phase: если Worker стартует с page 1 и ему нужна page 8, он выбирает ближайшую реально видимую страницу (например 7), ждёт callback, перечитывает pager и после появления ссылки переходит на 8.
